# Doc Review

## Overview

一个"发布前的事实预检"技能。它不替你改文档，只把源文档里可能出错的地方标出来，让你拍板。

适合用在：文档要拿去做视频 / 转写 / 对外发布之前，先过一道审；或者你怀疑随手记的笔记里有事实错误、命名不一致、结构缺陷时。

## When to use

- 用户明确要求"review / 核对 / 查一下准不准"某篇文档
- 在 narration-transcript 之类的转写技能执行前，作为可选预检步骤
- 文档是从某框架 / 库的官方资料整理的二手笔记，需要确认没把旧版用法、别名、过时说法带进来

## 红线与边界

1. **只标红，不动手改**：本技能产出 review 报告，绝不修改源文档。是否修、怎么修由用户决定。
2. **核对靠权威源，不靠印象**：任何事实断言都要对照权威资料核实（官方文档、规范、项目接入的 MCP、官方源码），禁止凭记忆下"这应该是错的"。
3. **通用化**：检查规则必须适用于任意文档，不绑定任何特定框架 / 项目 / 专有名词。示例一律用中性占位（如"某配置项""某条目名""某方法"）。
4. **改 markdown 一律用 Edit 工具**：如用户后续授权修改，用 Edit；禁止写脚本去改 markdown 文件。

## Workflow

### 1. 读源文档真实状态
先读当前文件（注意可能是符号链接，别破坏链接）。以文件里**现在的内容**为准，不依赖历史对话里的旧版。

### 2. 确定权威核对来源
- 优先用项目已接入的相关 MCP（如框架官方文档 MCP）
- 没有 MCP 时，用 WebFetch 拉官方文档 / 规范原文
- 关键源码级断言（字段名、类型签名）可拉官方仓库源码确认
- 找不到权威源的事实，标为"无法核实"，不强行下结论

### 3. 事实准确性核对
逐条核对文档里的硬事实：
- 名称 / 术语是否和官方一致（方法名、模式名、枚举值）
- 参数名、版本号是否准确
- 关键断言（"X 依赖 Y 才触发""X 在 Z 之后发生"）是否与官方描述一致
- 示例代码能否对应官方示例（方法名、参数是否拼对）

### 4. 内部一致性 / 结构 / 格式 / 时效扫描
- **内部一致**：同一文档内名词 / 字段是否前后统一；同一概念是否两种写法（如 `item` 与 `items`）
- **结构**：标题层级是否连续、有无跳级；章节是否挂错层级；有无悬空引用
- **格式**：markdown 语法合法性——表格分隔 / 对齐；图表语法里是否误用分隔符（如时间线事件文本里的半角冒号会被当成分隔符）；重复字、空占位符、错别字
- **时效**：是否把"早期 beta / 实验性"当成稳定功能；涉及版本差异时是否标注版本前提

### 5. 输出 review 报告
写一份独立报告文件（如 `<源文件名>-review.md`），按"实质问题 / 轻微问题"分级，每条给：
- 位置（行号或段落）
- 问题性质（事实 / 一致性 / 结构 / 格式 / 时效）
- 核实依据（哪份官方资料、具体说法或行号）
- 建议改法
- 置信度（高 / 中 / 低）
**不要**在报告里直接改源文档。

### 6. 交付与边界
- 把报告交给用户，由用户决定修不修
- 用户授权改源时，改用 Edit 工具逐条修，改完 grep / 读回验证无残留
- 通用检查维度清单见 `references/checklist.md`
