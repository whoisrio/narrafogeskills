# Visual Brief Design:技术信息可视化导演

技术旁白的结构是 `概念 -> 关系 -> 变化`,不是 `角色 -> 动作 -> 情绪`。
导演职责:**让信息动**(版面运动 + 图形语义承接语气转弯),不是让角色动。
每一个名词 -> 一个可视元件;每一个动词 -> 一种视觉动作;每一个逻辑关系 -> 一种空间关系。

## 背景不动，信息轰炸

两条分开理解：

**背景不乱动**：禁止为动而动的装饰运动（漂移光球/火花/镜头无目的晃动/环境呼吸）。背景干净，不抢信息。唯一该动的是信息本身。

**信息持续轰炸**：节奏要强，信息密度要高。每秒都有新信息/新变化入（新元素出现/状态变化/对比切换/焦点转移），让观众持续接收。不是"静态等待读懂"--是"信息密集推进"。只有关键结论需要观众消化时短暂 hold（1-2s），然后立刻继续。

一句话：**背景安静，信息密集。不是"少动"，是"动得有意义且密集"。**

## 工作流

### 第 0 步:查素材（项目 public/ + 原始文档）

旁白是从原始文档来的。原始文档里作者可能已经用 mermaid 流程图、代码块、表格把概念可视化了一遍--这些是**作者亲自做的可视化**,比导演重新编的更贴合内容。导演的活是找到它们、让它们动起来,不是重新发明。

**查两个来源:**

**A. 项目 public/ 目录**:截图/图片/图标/logo
- 有真实素材 -> 标来用(标文件路径),比编的图形有说服力
- 截图是内容证据(公告/界面/数据),优先于抽象图形

**B. 原始文档(旁白的来源文档)**:

**如何找到原始文档**(按顺序尝试):
1. 用户提供了原始文档路径 -> 直接用
2. 没提供 -> 查项目 `docs/` 目录,找与旁白主题相关的 `.md`/`.docx` 文件
3. SRT 文件名线索: SRT 叫 `02._一、三代_API.srt` -> 在 `docs/` 找含"三代"/"API"/"Completions"的 `.md`
4. 查项目里 `*旁白*`/`*narration*`/`*script*` 的文件 -> 旁白稿通常和原文档放一起或有引用
5. 查 README 或项目说明 -> 可能有原文档链接
6. 仍未找到 -> **问用户:"旁白的原始文档在哪？"** 不要跳过这步凭空设计

找到后逐段翻,找作者已有的可视化素材:
- **Mermaid/流程图**:作者已经画好的架构图/流程图/时序图 -> 直接改编成动画流程图(节点+边+流动),不要重画
- **代码块**:作者写的示例代码(JSON/Python/Shell) -> 标出代码块 id + 内容,交给 explainer 用 CodePanel 逐行展示
- **表格**:作者做的对比表(参数/配置/差异) -> 标出表格内容,交给 explainer 用 Table 组件动画展示
- **列表/分类**:作者已经结构化的清单(如"五种痛点""六个改进") -> 直接作为 feature_list 的内容,不要重新提炼
- **内嵌图片**:文档中的示意图/截图 -> 标出,同 public/ 截图处理

**判断规则**:这个旁白段落在原文档里有没有对应的可视化素材(图/代码/表)?有就标来用,没有才自己设计。

### 第 1 步:识别旁白结构

通读全部旁白,识别整体叙事结构。结构决定视觉节奏。
常见技术旁白结构:
- 复盘+辟谣:发布事实 -> 附加动作 -> 抛疑问 -> 泼冷水破除误解 -> 收束底层判断
- 原理推导:定义 -> 推导 -> 结论
- 对比分析:方案A -> 方案B -> 差异 -> 结论
- 演进叙事:一代 -> 二代 -> 三代 -> 趋势

### 第 2 步:定视觉系统(风格无关)

分镜前先定本片的信息系统(**不写颜色/字体,那些是 explainer 的活**):
- **信息元件类型**:本片用哪些容器(version_tag/api_block/flow_node/timeline/graph/table/myth_stamp/funnel/...)
- **焦点控制 + 镜头语言**:元素级用 focus(高亮目标+其他dim)/split(并排对比)/stamp(否定盖章)/hold(短暂停顿)控制注意力;范围变化(局部↔整体)用镜头语言(拉远/横移/推近,见「镜头语言」节),靠父 Group 变换模拟,内容驱动不滥用
- **维度(渲染)**:本片以 2D 为主,还是某些场景需 3D(Three.js)?遇到 embedding/架构层次/形态 morph/爆炸视图/真实运镜时标 `维度:3D`(见「3D 效果」节)。维度与视觉风格(doodle/sticker)正交,可任意组合
- **themeRef(可选,只写引用不写色值)**:如果用户提前定了风格,写一行 `themeRef: <theme id> + <engine>`,如 `playful + doodle`。没定就留空,由用户在 brief 完稿时从候选挑或 explainer 用默认。
  - 推荐来源:主题目录索引 `narraforgeskills/skills/theme-catalog/theme-catalog.md`(人读)/`.json`(机器读)。按内容情绪匹配 1-3 个候选给用户挑,候选按语气定:轻松→playful、复古复盘→retro-zine、发散 workshop→scatterbrain、教育科普→daisy-days、模块参数→capsule、手册严谨→stencil-tablet、锐利断言发布→block-frame/creative-mode(sticker 专属)。
  - **组件词必须引擎族级抽象**(callout/divider/connection/emphasis),不得写某个引擎专属形状(如"rough 手绘卡片"或"硬偏移方块"),否则 sticker 引擎映射不了。

### 第 2.5 步:划分场景

**场景 = 同一空间布局 + 一个戏剧目的。** 以下任一变化就是新场景：布局变了、戏剧目的变了、时间跳了。

**cue = 驱动场景内元素的变化**（出现/高亮/morph/消失）。场景内布局不动，cue 只改元素状态。

**场景约束（像动作电影导演一样思考）：**

1. **场景时长 3-8 秒**。超过 8 秒大概率塞了多个戏剧单元，该拆。
2. **每场景 3-6 个 cue**。超过 6 个 = 场景过载，观众需要换口气。每个 cue 驱动一个元素变化。
3. **一个场景 = 一个空间布局 + 一个戏剧目的**。布局变了或戏剧目的变了 = 新场景。例：缺失清单（列举缺失）和笔友类比（类比讲解）是两个戏剧目的，即使旁白连续也该拆成两个场景。
4. **节奏靠场景长度变化**：长(8s铺垫) + 短(3s爆发) + 中(5s呼吸) = 有节奏。全是同样长度的场景 = PPT。
5. **转场是节拍**：硬切=紧迫、滑动=推进、淡入=换话题。转场类型本身参与节奏构建，不是随便选的。
   **高级转场**（语义更强，按需选，实现配方见各引擎 motion-recipes）：
   - **穿窗**：页面内元素放大成全屏窗，新场景从窗内长出——**概念总览→该概念深讲**（"点开这张卡进入它的世界"）
   - **虚焦接力**：前景滑出焦平面、后景反向收焦——同一系统内区块→区块切换
   - **黑场字卡**：淡黑场+字卡蓄力再交棒——章节级分段，配三拍"引入"
   - **甩镜转场**：糊帧换景——强转折/章节切换（与镜头词 whip 的区别：这是转场用法，词写在场景 `转场` 字段）
   转场规则：**一个接缝只用一式**；转场占用的帧从相邻镜头预算划走；出入方向连续（出与入同向，速度曲线不回摆）。
6. **hold/rest 帧预算前置**：排 cue 时间线时先划走呼吸帧（结论落定 hold 1-2s、批量入场收尾静止 0.5s、转场帧），再排动效——不是排完动效再找空隙。
7. **整画面级冲击限量**：作用于**整画面/整场景**的冲击——震屏、全屏闪帧、整屏 slam——全片 ≤3 处。**砸在单个元素上的 stamp/✗ 章和 rush-in 出场是元素级动作，不计入**（多了只犯"词汇单调"，不犯"画面抖动"）。多了读作节拍式画面抖动。

**拆场景的方法**：通读 cue 列表，找布局需要变或戏剧目的变了的断点。每个断点切一个新场景。不要为了减少场景数而硬塞不同布局/不同目的的 cue 到一个场景里。

**段落级视角（多段长片时）**：场景是最小单位，段落是更大一层。先按"旁白意图→素材形态"表给每个段落定目标 atom（A/B/C/D/E），再在段落内按三拍结构（引入 5-10s → 主体 30-50s → 收束 5-10s）组织场景。节奏感由段落结构保证，见下方「段落级节奏结构」一节。

**场景切分贴合音频分段**：场景边界要对齐 SRT cue 边界，尤其是 cue 之间的停顿处。
- 转场动画（fade/slide/硬切）放在 cue 之间的间隙里，不要在 cue 中途切（旁白说到一半画面换场景 = 干扰）
- SRT 的 cue 分段本身就是音频的自然节奏--语气停顿、换气、话题转折都在 cue 边界上
- 场景内的 cue 连续播放（不停顿），场景间利用 cue 间隙做转场

**过渡旁白的处理**：有些 cue 是过渡性的（"不过"/"说白了"/"那么问题就来了"/"打个比方"），它们不引入新概念，是场景间的桥。这类 cue 不需要新元素，画面做的是**场景转场动画**：
- 转折词（"不过"/"但是"）：旧元素 dim + 画面轻微 shake
- 递进词（"第二代"/"再说"）：旧元素滑出 + 新空间从另一侧打开
- 预告（"扒完再下结论"）：旧元素 dim + 预告内容大字短暂闪现
- 收束（"仅此而已"）：当前场景所有元素整体缩小+淡出
- 类比引入（"打个比方"）：旧元素淡出 + 类比场景第一帧开始建

过渡旁白 = 转场动画的配音。旁白说过渡词的同时，旧场景在退场、新场景在进场。

**确认类旁白的处理**：另一类容易画崩的 cue 是**确认/肯定**（"相信你已经会了""你都掌握了""就这么简单"）——它**不是转场词**，不引新元素、不引转场，是对**旧知的肯定**，时长常 2-4 秒。**设计原则：已有元素做"肯定性"动效。不引新元素、不清场、不空屏。** 按时长选套路：
- **逐个确认**（2-4s）：已有元素依次弹一下/打 ✓（stagger 0.8-1s 一个），"你都会了"用视觉逐项确认。例：三张卡依次亮一下，正好填满 3 秒
- **聚合收拢**（2-3s）：元素轻微向中心聚拢 / 整体 scale 0.97，"已成体系"的收束感，不是清场
- **角色反应**（有 mascot 时）：吉祥物点头/pulse/竖拇指，拟人化确认
- **标记确认**（3-4s）：给元素贴"✓ 已掌握"类标签，确认感最强
- **焦点巡礼**（2-3s）：焦点在元素间游走一遍（亮→dim→亮），"这些你都见过"

**三个不能**：确认 ≠ 清场（清场是下一个转场句的活）；确认 ≠ 引新元素（无新信息，硬塞 = 失真）；确认 ≠ 空屏（画面必须有焦点在动，否则 = PPT）。

每个场景定义：
- **场景布局（场景构件表）**：先给本场景每个形状起稳定名字 + 标形状 + 标默认锚点，再写相对空间关系。Seg 里的连线引用这些名字，避免每句重命名导致实现对不上。例：
  ```
  构件:
    - api_block_A: 矩形块(w≈360), 左下, 锚点[上/下/左/右]
    - input: 小矩形(w≈200), api_block_A 正下方
    - output: 小矩形(w≈200), input 右侧
  ```
  （不写精确坐标——坐标由 explainer 根据组件实际尺寸+安全区+碰撞检查算。）
- **元素生命周期**：每个元素何时出现、何时消失（跨场景必须显式 fade out）
- **节奏标签**：铺垫/爆发/呼吸/收束（标注这个场景在全片节奏曲线里的位置）
- **转场方式**：硬切/滑动/淡入（从上一场景怎么过渡过来）

**布局职责分工**：导演定相对关系（谁在左谁在右、竖排还是横排）+ 给形状起名 + 标连线锚点，explainer 算精确坐标 + 验证碰撞。

### 第 3 步:逐句分镜 + 隐藏动词映射

**铁律：每一句旁白都必须有对应的视觉变化。**

不是"每句弹一个新元素"（那就是 PPT）。视觉变化包括：
- **出现**：新元素 pop in（新概念引入时）
- **高亮**：已有元素 pulse/glow/scale-up（被旁白提到时）
- **变化**：已有元素 morph/颜色突变/状态切换（旁白说"变成/切换"时）
- **连接**：箭头生长/连线出现（旁白说"流向/调用"时）
- **消失**：元素 fade out（旁白转向新话题时）
- **移动**：元素位移/重新排列（旁白说"对比/重组"时）

**什么内容可以不配动效**（例外，需显式判断）：
- 纯语气词/过渡词（"那么"/"说白了"/"对吧"）-> 不配独立动效，但前一个动效延续到这里
- 同一信息的换角度复述（"换句话说"）-> 不配新动效，已有元素保持
- 明确的停顿/留白（"..."）-> 有意为之的呼吸点，画面保持

**注意**：确认/肯定类（"相信你已经会了""你都掌握了"）**不在例外里**——它有 2-4s 时长、是独立的语气单元，必须配"肯定性动效"（逐个确认/聚合收拢/角色反应/标记确认/焦点巡礼，见上方「确认类旁白的处理」）。把它归进"不配动效"是常见的画崩来源（画面空 3 秒）。

除以上三种例外，**每句都必须有动效。没有动效的句子 = PPT。**



**每句旁白 = 一个 segment**(细粒度,不是几句话合成一大拍)。对每句:

1. **实体/属性/关系抽取**:旁白里的名词 -> 元件(API->api_block、模型->flow_node、命中率->gauge...)。关系(调用/依赖/大于/包含) -> 空间关系(连线/嵌套/并排)。
2. **识别隐藏动词 -> 映射视觉动作**:查下方「动词->动作源表」。旁白里的"发布/支持/阉割/错/扒/指向"都是隐藏动词,各对应一种视觉动作。
3. **写可画面化分镜(场景几何三要素)**:每句分镜必须把"屏幕上有哪几个形状、各自在哪、彼此怎么连"写清楚——这是 explainer 落代码的依据,连线不写清实现就靠猜,最容易画崩。**必须能让读者在脑中画出这一帧**。三要素:
   - **物体(有什么)**:本 Seg 出现哪些形状,各叫什么、是什么元件类型(api_block/flow_node/arrow_flow…)、什么几何形状(矩形/圆/胶囊/箭头/树)。
   - **位置(在哪)**:相对场景布局说清每个物体落在哪(谁左侧/谁上方/屏幕中下/竖排第几条…),不写精确坐标——坐标由 explainer 算。
   - **连线(怎么连,仅当物体间有连接时)**:明确"连线从哪个物体的哪个锚点出 → 用什么动画生长 → 连到哪个物体的哪个锚点"。锚点用 上/下/左/右/右上/中心 这类方位词,**不写坐标**。例:"虚线箭头从 input 块右锚点生长,连到 output 块左锚点"。
4. **焦点指令 + 镜头**:元素级用 focus(高亮目标+其他dim)/split(并排)/stamp(否定)/hold(停顿) 引导注意力;范围变化(局部→整体等)用镜头语言(拉远/横移/推近),写进场景 `镜头` 字段,内容驱动、不滥用。

### 第 3.5 步:音画偏移策略

动画不应该和旁白严格同步对齐,要有意识地提前或滞后,制造认知节奏:

| 策略 | 偏移量 | 适用场景 | 效果 |
| --- | --- | --- | --- |
| **提前(视觉先行)** | 0.3-0.5s | 新概念引入、图表/架构图出现、转场 | 观众先看到画面,旁白再解释,视觉铺垫认知 |
| **同步** | 0s | 代码逐行、列表逐条、连续信息流 | 跟着旁白节奏推进,不抢不拖 |
| **滞后(语言先行)** | 0.2-0.3s | 否定/stamp、强调/punch、结论金句 | 旁白先说出,视觉再砸下来,"等一下...嘭" |

规则:
- 引入新概念(新 API 块/新图表/新节点)-> **提前 0.3s**(观众先看到,再听解释)
- 否定/辟谣(stamp/shake)-> **滞后 0.2s**(旁白说"错!",0.2s 后红章砸下)
- 结论/金句落版 -> **滞后 0.3-0.5s**(旁白说完,视觉再落定,有余韵)
- 代码逐行/列表逐条 -> **同步**(跟旁白节奏)
- 转场(beat 切换)-> **提前 0.3s**(视觉先动,旁白跟上)

每段分镜标注偏移策略,explainer 实现时在 delay 上加减对应帧数(30fps 下 0.3s=9 帧)。

### 第 4 步:分段输出（按 SRT 文件）

**每个 SRT 文件 = 一份独立 brief。** 不要把整片所有段塞进一个文件。

输出结构：

```
# 全片设计概要（20 行以内，管跨段一致性）
  色码贯穿: <各概念的全片色码>
  全片节奏: S1(铺垫) -> S2(演进) -> S3(爆发) -> ... -> SN(收束)
  跨段元素: <哪些元素横跨多段，需保持位置/色码一致>

# S1 brief（对应 01.srt，200-400 行）
  场景1: ...
  场景2: ...

# S2 brief（对应 02.srt，200-400 行）
  ...
```

**全局概要**保证跨段一致：色码不换、节奏曲线连贯、跨段元素（如 timeline）位置延续。
**各段 brief** 独立自包含：只管本段的场景/cue/动效，引用全局概要的色码和节奏定位。

**多 agent 协作模式**：分段设计可以拉起 sub agent 并行，主 agent 审核一致性。

- **主 agent**：
  1. 先产出全局设计概要（色码/节奏曲线/跨段元素）
  2. 每个 SRT 文件派一个 sub agent，给它：SRT 文件路径 + 全局概要 + 原始文档路径
  3. 收回各段 brief 后审核：色码对不对、节奏接不接得上、跨段元素位置连不连、场景约束（3-8s/3-6cue）满不满足
  4. 不通过则退回 sub agent 修改，通过则合并

- **sub agent**（每个负责一个 SRT 段）：
  1. 拿到 SRT + 全局概要 + 原始文档
  2. 按本 skill 流程产出该段 brief（查素材 -> 识别结构 -> 划场景 -> 逐句分镜）
  3. 只管本段，引用全局概要的色码和节奏定位，不擅自改跨段设定
  4. 返回该段 brief 给主 agent

- **审核清单**（主 agent 用）：
  - [ ] 色码与全局概要一致？（同概念同色）
  - [ ] 节奏与全局曲线衔接？（上一段收束 -> 本段开场，不断裂）
  - [ ] 跨段元素延续？（如 timeline 在上段画到哪、本段从哪继续）
  - [ ] 每段场景约束满足？（3-8s/3-6cue/一布局一目的）
  - [ ] 转场方式与节奏匹配？（硬切/滑动/淡入用对了地方）

## 表格设计（数据统计/参数对比必备）

信息容器库里已列 `table`,但表格不是"画个格子"就完事——它承载**行列关系 + 行间/列间对比**,需要专门的设计与动效套路。遇到下列旁白,优先想到表格而非堆卡片:
- 多组参数/配置横向对比(各模型的 context 长度、价格、速度)
- 多行记录(各版本变更、各指标数值)
- 分类汇总(按维度聚合的统计)

**brief 里怎么写表格**(并入场景几何三要素):
- **物体**:标明 `table` 元件 + 列数/行数 + 哪些列是表头/分组列。例:"table(3列×5行, 第1列=模型名表头, 第2-3列=数值)"
- **位置**:表格在屏的哪块(居中占满/左栏/右侧对照),与旁边元素的位置关系照常写
- **连线**:表格内部一般无连接线;但若某单元格要连到屏上另一元素(如"该数值对应右侧趋势图峰值"),按三要素写清从哪个单元格的哪个锚点→什么动画→连到哪

**表格动效套路**(写进 `出场方式` 字段):
- 表头先落:header 行先于数据行出现,定住列语义
- 逐行弹入:数据行按旁白节奏 stagger 逐行弹入(0.3-0.5s/行),别整张表同时砸下
- 单元格高亮:旁白提到某行/某列时,该单元格 pulse/描边高亮,其余 dim
- 列强调:对比两列时,目标列保持、其他列 opacity 0.3(列级 focus)
- 行重排/排序:旁白说"按 X 排序"时,行做位置插值重排(layout animation)
- 数字跳动:关键数值单元格做 count-up/数值滚动,比静态数字更有说服力
- 行增删:旁白说"再加一行"时,新行从下方插入、下方行下沉让位

## 出场动效库 (Entrance Animation Catalog)

现状问题:大量 brief 的出场方式全是"弹入(pop + spring)",单调。组件/标题的入场应**按内容语义选风格**,让每一拍的"出现"本身带信息。下面是可直接写进 `出场方式` 字段的动效词(风格无关,explainer 映射到本风格实现):

| 出场方式 | 视觉表现 | 适用语义 | Remotion 实现要点 |
| --- | --- | --- | --- |
| pop (默认) | spring 弹入,轻微 overshoot | 通用引入/新概念 | scale 0->1 + spring; 最稳妥,但别全片只用它 |
| slide / fly-in | 从某方向(左/右/上/下)滑入 | 元素"来自"某处(输入从下、调用从左) | translate + spring; 方向须与语义一致 |
| dissolve / fade | 溶解淡入,opacity 0->1 + 轻微 blur | 柔和出现/回忆/次要信息 | opacity + blur(8px->0); 不抢戏 |
| rush-in | 疾冲入场:fast scale + 方向位移 + 轻微运动模糊 | 强调"突然杀到"/爆发/冲击 | 短 duration(0.25s) + 方向 translate + 末帧 snap |
| typewriter | 逐字显现(文本类) | 代码/命令/逐字强调 | 字符 clip 或 Text 逐 char delay |
| flip | 3D 翻转登场(flip-up/down/left/right) | 卡片翻面/正负切换/揭晓 | rotateX/Y 0->180 配 backface; 注意厚度感 |
| wipe / mask | 擦除揭示(左→右/下→上 clip 推进) | 进度/范围展开/扫描 | clip-path / mask 动画 |
| stagger | 批量同类元素加速错峰入场(间隔递减+收尾静止 0.5s) | 并列清单/对比项/矩阵格子逐个登场 | 同动效 + 间隔递减(如 8f→3f)+收尾静止 0.5s; 可绑物理隐喻(发牌感); 等间隔读作机械复读,配方见引擎 motion-recipes |
| blur-in | 由虚变实(对焦) | 从模糊背景中"聚焦"出重点 | blur(12px)->0 + opacity; 常配 focus |
| draw / stroke | 描边生长(SVG path) | 图形/图标/轮廓先画出来 | pathLength 0->1 |
| scale-up | 由小放大(无 spring,平滑) | 平静放大/图表展开 | scale 0.6->1 ease |
| rotate-in | 旋转入场(2D 旋转落定) | 标志/章/圆形元素 | rotate(-180->0) + scale |
| shimmer / sweep | 扫光后浮现 | 高光/新功能/发布感 | 渐变扫过 + opacity |
| snap / magnetic | 磁吸归位(从偏移处弹回正位) | 元素"归位/吸附" | 大偏移 translate + spring 回 0 |

**标题动画**:每个场景/段落的标题是**一等设计对象**,不是永远"居中弹入"。标题出场方式应随内容挑:
- 章节大标题:rush-in 砸下 / flip 翻出 / scale-up 放大落定
- 小节标题:slide 从侧边滑入 / wipe 擦出 / typewriter 逐字
- 落版金句:scale-up + 轻微 overshoot + 余韵 hold
- 避免:所有标题都用同一种 pop,观众会脱敏

**选择原则**:
1. 出场方式要**服务语义**——"来自左侧的输入"用 slide-left,"突然杀到的结论"用 rush-in,"平静展开"用 scale-up,不是随机挑
2. 同一场景内避免连续 3+ 个相同出场,制造节奏变化
3. 全片出场方式分布要查(self-check):pop 占比过高的段落要换几种
4. 动效时长与语义匹配:rush-in 短(0.25s)、dissolve 中(0.5s)、typewriter 跟旁白

## 素材形态(visual_atom,供 explainer 选画法/素材来源)

每个 shot 除了标信息元件,还应标**素材形态**——它是"代码绘制"还是"真实素材",决定 explainer 走哪条路。5 类,精简版:

| atom | 形态 | 谁来画 | 备注 |
| --- | --- | --- | --- |
| A 概念示意 | 代码绘制(几何/卡片/隐喻图) | explainer(引擎画法) | 抽象概念用隐喻可视化,别用公式/学术图 |
| B 真实素材 | 截图/Logo/真实 UI | asset-generation 接入 | 需要真实物证时用,优先于抽象图形 |
| C 产物演示 | 真实产物(录屏/模型输出) | 项目 public/ 真实素材 | 讲"效果/看这个"时,必须是真产物,不用 mockup |
| D 数据/对比卡 | 代码绘制(大号数字/对比布局) | explainer | 大数字徽章 + 单位 + 上下文小字,每个数字停 0.8-1.2s |
| E 流程卡 | 代码绘制(横向色卡+箭头) | explainer | 章节预告/回顾用,3-5 张同色系,每章同套只换标签 |

**规则**:
- 抽象概念/数据/流程 → A/D/E(代码绘制,explainer 自由)
- 需要真实物证(界面/文档/产物) → B/C(asset-generation 或 public/),**截图保留光标,关键元素标 spotlight/箭头**
- A-E 是"素材来源"层,和信息元件库(画什么)是两层,不冲突:一个 shot = 元件(内容)+ atom(形态)

## 旁白意图 -> 素材形态 映射(6 类,挂在隐藏动词表旁做辅助)

隐藏动词表管"动作怎么动",本表管"这段旁白该用什么形态的素材"。识别旁白段落意图,选对应 atom:

| 旁白意图(段落级) | atom | 说明 |
| --- | --- | --- |
| 钩子/价值承诺("压到一毛""官方 1/8") | A 概念示意 | 首帧给价值可视化,别空镜 |
| 演示/看效果("先看一下""看这个") | C 产物演示 或 B 真实素材 | 真产物优先,不加 UI 框解释 |
| 操作步骤("点击/输入/选择") | B 真实素材 | 必须保留光标,关键按钮红箭头/黄 spotlight |
| 痛点/隐喻("不会用/很麻烦") | A 概念示意 | 把抽象痛画成具象画面(锁住的保险箱),用比喻替代解释 |
| 对比/取舍("X 比 Y 强""手动 vs 自动") | D 对比卡 或 A 汇聚图 | 上混乱/下秩序、多→一汇聚,视觉冲击 |
| 收束/回顾/重申("到这里我们已经…""核心数字") | E 流程卡 或 D 数据卡 | 极简留白,让结论/数字"砸"一下 |

**导演的工作**:先识别段落意图(钩子/demo/操作/痛点/对比/收束),再选 atom,再选信息元件。不编戏,只保证"每段有对的素材形态"。

## 段落级节奏结构(三拍,治"僵硬"的利器)

**每段 60-90 秒的旁白,按三拍组织视觉,节奏由结构保证而不是靠每帧画对:**

1. **引入(5-10s)**:概念示意(A)或流程卡(E),建立本段要讲什么
2. **主体(30-50s)**:真实素材(B/C)或代码绘制的主体讲解,信息密集
3. **收束(5-10s)**:数据/对比卡(D),或极简留白帧重申关键数字

**段间**:硬切为主,不做大转场——subtitle 跟着旁白走就是音画锚点。

**全片节奏曲线**:钩子(A) → 预告(E) → N 段[三拍] → 回顾(E) → 收束(A)。节奏感来自"每段都有引入-主体-收束"的结构,不是靠单个动效堆。

**合影式收尾**(可选,多概念长片推荐):收束段升级为"全家福"——全片已展示的每个概念各出一个代表元素,多方向飞入合围结论字标,能量推到全片峰值。比 converge 汇聚+大字落版更高级:既是收束又是全片回顾,天然满足"每句有动效"。跨段元素在这里各归各位,色码贯穿是它的骨架。

> 注:本结构适用于多段落长片(≥3 分钟)。单片短视频(≤60s)不强制,仍按场景 3-8s 规则组织。

## 焦点控制(元素级) + 镜头语言(组级)

引导注意力有两层,互不冲突:
- **元素级焦点**(本表):针对单个/一组元素的高亮、dim、morph,不变画面整体框取范围。
- **镜头语言**(下一节):对整个场景内容做"相机"运动(推近/拉远/横移),改变观众看到的框取范围。Remotion 无真相机,镜头靠**把场景内容包进一个父 Group,对该 Group 做 scale+translate 变换**模拟。代码绘制的矢量元素缩放清晰不受限;位图(public/ 截图)放大超过 ~1.3x 会糊,故位图优先用拉远/横移(缩放 down,清晰),推近默认 ≤1.3x——位图经引擎高清栅格化后可超(见引擎 motion-recipes)。

| 逻辑目的 | 焦点指令 | 实现 |
| --- | --- | --- |
| 引入新概念 | focus(新元素) | 新元素 pop in + 其他 dim(opacity 0.3) |
| 对比两个对象 | split(A,B) | CSS flex 并排两栏 |
| 强调关键参数 | pulse(元素) | 元素 scale 1->1.15->1 |
| 展示层级 | reveal(第N层) | 逐层 opacity stagger |
| 展示变化 | morph(A->B) | A crossfade 出 + B 弹入 |
| 否定辟谣 | stamp + shake | ✗ scale 3->1 + wrapper 振荡 |
| 揭示内部 | dim(外壳)+reveal(内部) | 外壳 opacity->0.25 + 内部 0->1 |
| 划重点/停下细看 | freeze + 圈注 | 帧号 remap 定格 + 马克笔描边圈住目标(配方见引擎 motion-recipes); 一支片≤2次 |
| 收束总结 | converge + 大字 | 多元素向中心位移 + 大字 pop |

注:镜头运动只用于内容驱动(局部→整体等),禁无目的装饰晃动(见设计原则3)。

**物体晃动 vs 镜头语言(务必区分)**:
- **镜头语言**(推近/拉远/横移/升降/orbit 等)是**内容驱动的范围变化**——框取从局部到整体、或焦点在 A/B 间转移。这是**允许且鼓励**的一等设计,写进场景 `镜头` 字段。
- **物体入场后的无目的晃动**(元素落定后还在上下/左右无意义抖动、无谓往复平移)是**禁止**的。已就位元素应保持静止,靠新信息推进维持活力。
- **唯一例外**:晃动若**服务于动画表达**,则允许——典型如错误反馈的 `shake`(否定 stamp)、情绪强调的振荡。即"为让画面活而加的晃动"不行,"为了说清一件事而抖一下"可以。这跟"背景不动"原则一致:动的是信息,不是装饰。

## 镜头语言 (Camera Language)

当旁白从局部讲到整体、或反之,用镜头运动承接"范围变化",比单纯元素缩放更有电影感。镜头写在场景层,且分两层:
- **场景级镜头弧**(写在场景 `镜头` 字段):描述这个场景从头到尾的**整体运镜意图**,如"近景引入(聚焦局部) → 拉远收束(露出整体关系)"。Seg 只是单句,看不到全貌,所以"近→远"这种跨多句的弧**必须站在场景层才完整**,不要拆碎了塞进某个 Seg。
- **Seg 级瞬时镜头**(写在对应 Seg 的 `镜头`):某个 cue 点具体的推近/拉远/横移,它必须**服从场景弧**(弧说"先近后远",Seg 就不能出现一个无关的推近打断它)。

可在场景内不同 Seg 之间切换镜头(如 Seg 前半聚焦局部、Seg 后半拉远),但**不在单个 cue 中途切镜头**(观众会晕)。

**镜头词表(写进场景的 `镜头` 字段)**:

| 镜头 | 表现 | 适用旁白 | 实现要点 |
| --- | --- | --- | --- |
| 固定 static | 不动,框取不变 | 通用/静态讲解 | 无变换 |
| 推近 push-in | 局部放大,框取收小到细节 | "深入看/仔细看/放大看 X" | Group scale 1->1.3 配 translate 到目标; 位图勿超 1.3x(高清栅格化后可超,见 motion-recipes) |
| 拉远 pull-back | 后撤,框取放大露出周围 | "除此之外/整体来看/还有这些" | Group scale 小->1(从局部占满到整体可见); **最常用且清晰** |
| 横移 pan | 沿水平/垂直滑动 Group | 对比两栏/时间轴推进/跟随焦点 | Group translateX/Y; 配合 split 很有用 |
| 升降 crane | 纵向揭示 | 从下往上层层揭示/从上鸟瞰全貌 | Group translateY + 轻微 scale |
| 环绕 orbit | 整体旋转 Group | 360 展示/多面呈现 | Group rotateZ; 多用于图标/产品 |
| 甩镜 whip | 快速 pan 制造冲击转场 | 强转折/章节切换 | 极短 translate + 运动模糊; 用于转场非内容 |
| 视差 parallax | 多层不同速度位移 | 制造纵深/层次感 | 前景/背景 Group 不同 translate 系数 |
| 焦点切换 rack | 前后景 blur 切换 | 从 A 焦点切到 B 焦点(非缩放) | 前 Group blur 升 + 后 Group blur 降 + opacity |
| 急推 crash-zoom | 快速推近+冲击落定 | 否定/惊结论("错!"/"就这么贵") | 快速 Group scale 冲到 1.2~1.3 + 末帧 snap; 配滞后音画偏移; 每场景≤1次; 是节奏冲击不是范围变化,与平滑"推近"区分 |
| 侧掠 side-glide | 内容自身滑过固定取景框(物动镜不动) | 长时间轴/长流程横排内容依次掠过 | 透视参数全程常数,唯一动的量是内容 translateX; 与横移(镜头动)正交,同段落二选一; ≥3屏宽横排内容适用 |

**镜头与场景边界**:每个场景的 `镜头` 默认 reset(场景1 的推近不影响场景2 构图)。跨场景需"连续镜头"(如场景1 拉远接到场景2 同一全景)时,在全局概要标注"镜头延续",explainer 衔接 Group 变换。

**安全与克制**:
- 镜头运动必须**内容驱动**(局部↔整体、焦点转移),禁无目的晃动(光球/火花/镜头乱晃)
- 缩放方向优先"放大框取范围"(拉远/横移);推近默认 ≤1.3x,矢量不受限,位图经引擎高清栅格化(见 motion-recipes)后可超
- 一个场景内镜头变化不超过 2 次,多了观众会晕
- 镜头变换通常配转场(硬切/淡入)或 cue 间隙,不抢旁白

## 3D 效果（Three.js / react-three-fiber）

当内容本身带**空间/体积/深度**关系,或**相机运动就是叙事**时,2D 会勉强、3D 才自然。本 skill 的 2D 渲染是 Remotion 代码绘制;3D 场景则由 explainer 在 Remotion 内嵌 `<Canvas>`(react-three-fiber + drei) 渲染,几何/材质/相机由 Three.js 驱动。**3D 是一个独立的"维度"轴,与视觉风格(doodle/sticker)正交**——同一个 doodle 手绘风也可以长在 3D 场景里(贴图/材质走手绘感即可)。

**什么时候该用 3D(选型清单)**:

| 内容特征 | 为什么 2D 不够 | 3D 怎么解 |
| --- | --- | --- |
| 高维/向量空间(embedding、聚类、manifold) | 2D 只能投影丢维度 | 3D 点云/散点,真实呈现距离与簇 |
| 系统/架构有"前后/内外"层次 | 2D 扁平,背面的东西得靠切图 | 3D 积木 + 真实深度,镜头绕到背面 |
| 数据是三维的(长宽高/XYZ 对比) | 2D 柱图压成 2 维 | 3D 柱/体/曲面,第三维直接看 |
| 形态变化(state morph) | 2D 只能 crossfade 假装 | 3D 几何体真 morph(球→方→其他) |
| 内部结构的"拆解/爆炸" | 2D 只能 dim 外壳露一层 | 3D 爆炸视图,零件沿轴飞开 |
| 数据流/信息流要"有体积地涌动" | 2D 箭头是线 | 3D 粒子流/管道,数据在空间里流 |
| 相机运镜本身就是信息(从单点拉到全局网) | 2D 只能伪造 Group 缩放且易糊 | 3D 真实 perspectiveCamera,推/拉/环绕都干净 |
| 产品/分子/设备 360 展示 | 2D 只能多张图轮换 | 3D 模型 orbit 一圈 |

**3D 效果词表(场景标 `维度:3D` + 复用 `镜头`/`出场方式` 字段)**:

| 效果 | 表现 | Remotion/Three.js 实现要点 |
| --- | --- | --- |
| point-cloud 点云 | 大量小点构成空间分布 | `<Points>` + BufferGeometry; 颜色按簇/距离编码 |
| mesh/surface 曲面 | 3D 地形/损失曲面/热图 | `<Mesh>` + planeGeometry + 顶点位移; 颜色映射数值 |
| particles 粒子流 | 数据/ token 在空间流动 | `<Points>` + 每帧更新 position; 可加 curl-noise 轨迹 |
| 3D bars/volumes | 三维柱/体对比 | instancedMesh 排阵列; 高度=数值 |
| geometry-morph | 几何体真变形 | morphTargets 或两 mesh 间 lerp(球→方) |
| exploded-view 爆炸视图 | 零件沿轴飞开露内部 | 各子 mesh 沿法线/轴 translate 开; 反向合拢 |
| 3D node-graph | 节点在 3D 空间连边 | 节点=mesh, 边=TubeGeometry/Line; ForceGraph3D 思路 |
| physics 物理 | 弹簧/重力/碰撞的因果感 | @react-three/rapier 或简单 verlet; 块堆叠/掉落 |
| bloom/glow 体积辉光 | 3D 空间里的强调 | postprocessing + UnrealBloomPass; 强调点发光 |
| orbit/真实运镜 | 推/拉/环绕/升降=真相机 | perspectiveCamera + 改 position/lookAt; 与 `镜头` 字段一一对应 |

**3D 场景里的镜头语言**:前面「镜头语言」节的镜头词表(推近/拉远/横移/升降/环绕/视差/焦点切换)在 3D 场景里由 **Three.js 真实相机**执行——比 2D 的 Group 伪造更自然,且 环绕(orbit)、真实景深(rack focus via DOF)、推近不糊(矢量渲染)都直接成立。`镜头` 字段写法不变,只是实现从"父 Group 变换"换成"相机变换"。

**安全与克制(比 2D 更要注意)**:
- **只为空间/体积/相机叙事上 3D**,不为炫技。能用 2D 清楚讲的不上 3D(2D 更快更稳)。
- **禁装饰性粒子/光尘**:粒子流必须承载信息(数据/token),背景不能飘无意义的光点——这跟"背景不动"原则一致。
- **数量克制**:全片 3D 场景控制在少数几个高潮/关键概念,别通片 3D(性能+注意力都扛不住)。
- **混合场景**:2D 前景文字/标题 + 3D 背景层可共存(HTML overlay + Canvas),brief 里标清哪层 3D 哪层 2D。
- **实现前提**:3D 场景需要 explainer 支持 r3f 渲染路径(本 skill 只设计,不实现);标 `维度:3D(Three.js)` 即提示走该路径。

**brief 写法**:3D 场景在场景层标 `维度(渲染): 3D(Three.js)`,`物体` 几何写 3D 形状(球体/立方体/点云/网格/管道/3D节点),`镜头` 用真实相机运动,`位置` 写 3D 空间相对关系(前/后/左/右/上/下 + 远近),其余三要素(连线/分镜/音画偏移)照常。

## 文字两态(要读 vs 纹理)

分镜里每块文字标明两态之一,**无中间态**:
- **要读**(字幕/关键词/结论/数据):explainer 保证有效字高(渲染帧实际像素,字幕 ≥56px/辅助 ≥32px 口径由引擎执行)与足够对比度
- **纹理**(装饰性小字/截图内小字/背景文字):明显虚化/降亮度,让观众不去读
- 导演的活是决定**哪块字要读**;字高数值是 explainer 的活。未标注的文字默认"要读"。
- 标注方式:在 Seg 的 `分镜` 描述或物体名后标 `(要读)`/`(纹理)`,如 "落版大字'仅此而已'(要读)"。

## 布局规范

**导演定相对关系,explainer 算精确坐标 + 验证碰撞。**

导演在分镜里写相对空间关系(左/右/上/下/居中/竖排/横排/并排),不写精确 x/y/w/h。如果尺寸有语义(截图宽高比/代码行数),标注出来供 explainer 参考。

explainer 实现时负责:
- 根据组件实际尺寸 + 相对关系计算精确坐标
- 安全区:四周边距 ≥80px,底部 ≥54px
- 不重叠:同时出现的元素 bounding box 不相交(引线/箭头除外)
- 间距:相邻元素 ≥40px
- 渲染静帧后程序化验证(bounding box 检查),不通过则定点修

## 否定要带证据

否定一个观点时,**不只盖 ✗**。盖章后立刻对比展示实际差异,让观众知道**为什么错**。
例:否定"Responses = 升级版 Chat Completions"后,并排展示:
- Chat Completions: 无状态 / messages[] / 推理丢弃
- Responses: 有状态 / items[] / 推理保留
- 用 ≠ 连接

## 设计原则

1. **讲结构不讲故事**:概念->关系->变化,不编剧情角色
2. **隐藏动词直译为视觉动作**:不编戏,只把旁白里的动词映射成图形动作
3. **背景不动+信息轰炸**:背景禁装饰晃动(光球/火花/镜头乱晃);信息要持续轰炸(节奏强、每秒有新变化),不是静态
4. **否定带证据**:不只 ✗,对比展示为什么错
5. **呈现设计可画面化**:具体分镜(物体/位置/形状/运动/连线锚点),禁概念口号
6. **真实素材优先**:先查 public/,有截图就用,比编的图形有说服力
7. **风格无关**:不写颜色/字体/组件实现,交给 explainer
8. **逐句分镜**:每句旁白一个 segment,细粒度,不一拍坐 10 秒
9. **一个时刻一个焦点**
10. **旁白是节奏锚点**:动效对齐 cue 时间戳
11. **每段有对的素材形态**:识别段落意图(钩子/demo/操作/痛点/对比/收束)选 atom(A/B/C/D/E),见「旁白意图→素材形态」表
12. **多段长片按三拍组织**:引入(A/E) → 主体(B/C 或代码) → 收束(D/留白),节奏由段落结构保证,见「段落级节奏结构」
13. **出场方式服务语义且多样化**:按内容挑 pop/slide/dissolve/rush-in/typewriter/flip/wipe 等,不全程弹入;标题动画是一等设计对象
14. **表格用于数据统计/多列对比**:行列关系/行间列间对比用 `table` + 表格动效,不硬堆卡片
15. **镜头语言内容驱动**:局部↔整体的范围变化用镜头(拉远/横移/推近)承接,禁无目的晃动;推近≤1.3x
16. **3D 只为空间/体积/相机叙事**:embedding/架构层次/形态 morph/爆炸视图/真实运镜才上 3D,不为炫技;装饰性粒子/光尘仍禁(与"背景不动"一致)
17. **物体入场后禁无目的晃动**:元素落定后不无谓抖动/往复平移;若需晃动(错误 shake/情绪强调)必须服务表达,否则静止靠新信息推进——这与镜头语言(内容驱动的范围变化)是两回事,勿混为一谈

## 参考示例

> **示例里的颜色(金色/青绿/灰蓝等)只是示意"强调什么",不是让你写死色值。** 落成片时由 explainer 从 theme 对象填色(themeRef 指定),导演只负责标"哪个元素该强调"。

### 示例 1：开场钩子（出现 -> 现实场景切入）

旁白："以图搜图的原理是什么？为什么电商搜同款？"
- 实体：以图搜图(概念) / 现实操作(观众已知)
- 动作：钩子 = 出现 -> real_scene.slide_in（用观众已知的东西开场，不用术语）
- 焦点: static
- 分镜：画面中央放一个真实笔记本电脑实物图 + Google 搜图界面截图。界面上的搜索框和结果页清晰可见。底部弹出大字"以图搜图"（,,色差错位效果）。不出现任何技术术语（不出现"向量""embedding"）。
- 出场方式: 实拍图 slide-in; 落版大字 pop(色差错位)
- 音画偏移：同步（钩子问题与视觉同时出现）
- 素材：真实笔记本照片 + Google 搜图界面截图

### 示例 2：算法流全景（流动 -> 一镜到底箭头串接）

旁白："拍照搜同款，背后是向量检索：先把图片变成向量，然后在上亿个向量里找最相似的。"
- 实体：拍照 / 向量 / 距离 / 匹配
- 动作：流过 = 流动 -> arrow_flow 串接（一镜到底，空间布局即算法时序）
- 焦点: focus 从左到右沿流程转移(当前节点高亮+其他dim)
- 镜头: 横移(沿流程从左到右跟随焦点,用镜头走完算法时序)
- 连线: 拍照→向量→距离→匹配: 每两节点间 虚线箭头 生长(从左到右),无交叉
- 分镜：四个 flow_node 从左到右横排：拍照(,,青绿色) -> 向量(,,青绿色) -> 距离计算(,,深蓝色) -> 匹配结果(,,金色光晕+星星)。节点按从左到右依次弹入(stagger 0.5s)。每两节点间虚线箭头生长。匹配结果节点最强视觉权重(金色+发光+星星)。入场顺序：节点(骨架)先->箭头(连接)次->星星装饰(强调)最后。
- 出场方式: flow_node stagger 弹入(0.5s); 箭头 draw 生长
- 音画偏移：提前 0.3s（第一个节点先于旁白出现）
- 素材：无

### 示例 3：概念对比（对比 -> 同一视觉元素+标签替换）

旁白："Harness Engineering 和提示词工程什么关系？和上下文工程又是什么关系？"
- 实体：Harness Engineering / 提示词工程 / 上下文工程（三个概念，同族）
- 动作：什么关系 = 对比 -> same_element.tag_swap（同一视觉元素+标签替换）
- 焦点: static
- 分镜：画面中央一匹战马角色（,,w=400,始终保持不动）。马身上挂一个标签胶囊。旁白每提到一个概念，标签 morph 替换：第一个"Harness Engineering"(紫色) -> 第二个"提示词工程"(绿色) -> 第三个"上下文工程"(青绿色)。每次替换时标签 scale-down -> 文字变 -> scale-up。马不变=这三个概念是"同族"。
- 出场方式: 标签 scale-down→文字变→scale-up(morph 替换); 战马 保持不动
- 音画偏移：同步（标签随旁白提到时替换）
- 素材：战马角色图

### 示例 4：组件组合（包含 -> 拼装动效）

旁白："CLAUDE.md 加上插件，就是 Harness Engineering。"
- 实体：CLAUDE.md(配置文件) / 插件(组件) / Harness Engineering(系统)
- 动作：加上 = 组合 -> assemble（组件+组件=系统，拼装动效）
- 焦点: static
- 连线: 无(三块向中央滑动汇聚拼装,非连线)
- 分镜：左侧一个红色主题的配置文件块"CLAUDE.md"。右侧两个插件块"插件A""插件B"(,/,w=200,h=80)。三块同时向中央滑动汇聚，拼成一个大的系统块"Harness Engineering"。拼合瞬间有一个"咔哒"弹跳。
- 出场方式: 三块 slide 向中央汇聚; 系统块 pop(咔哒弹跳)
- 音画偏移：提前 0.3s（组件先开始滑动，旁白说"加上"时拼合）
- 素材：无

### 示例 5：层级堆叠（层级 -> 垂直堆叠+色码区分）

旁白："解码器由这些组件组成：带掩码多头注意力、Add & Norm、多头交叉注意力、FFN。"
- 实体：掩码多头注意力 / Add&Norm / 交叉注意力 / FFN（四层组件）
- 动作：组成 = 层级 -> vertical_stack（垂直堆叠+色码区分）
- 焦点: focus(底层先亮,逐层往上)
- 镜头: 近景引入(开场聚焦底层组件占满屏) → 拉远收束(退到整张四层堆叠全貌)
- 连线: 无(垂直堆叠为包含关系,非连线)
- 分镜：四个矩形块从下到上垂直堆叠（,-700,每块 w=500,h=90,间距 10px）。从下到上依次弹入(stagger 0.4s)。每块不同色码：FFN=青绿色(底) -> 交叉注意力=深蓝色 -> Add&Norm=橙色 -> 掩码多头注意力=深蓝色(顶)。每块左侧标组件名(mono字体)，右侧标色码圆点。外框最后弹入（大圆角矩形框住四块）。镜头开场贴在底层(FFN)上占满屏,随逐层弹入父 Group 缓缓拉远,收尾退到能看全四层+外框的全貌。
- 出场方式: 矩形块 stagger 从下到上弹入(0.4s); 外框 scale-up 落定
- 音画偏移：提前 0.3s（底层块先于旁白出现）
- 素材：无

### 示例 6：失败路径否定（否定 -> 红色X + 色码对比）

### 示例 7：3D 向量空间（空间关系 -> 点云 + 真实推近）

旁白："以图搜图，本质是把图片变成向量，再在一亿个向量里找最近的那个。"
- 维度(渲染): 3D(Three.js)
- 实体：查询图片向量 / 向量空间(点云) / 最近邻簇
- 动作：空间关系 = 点云分布 -> push-in(从查询点推到最近簇)
- 镜头: 拉远(开场全空间) -> 推近(落到查询点再拉向最近簇)
  - 注:本例是「整体→局部」(先拉远见全空间,再推近到查询点),与示例 9 的「局部→整体」(近景→拉远)方向相反,两种都常用,视旁白从哪讲起。
- 分镜：开场镜头在 3D 点云中拉远,看到漫布全空间的彩色点(按类别着色)。旁白说"图片变成向量"时,中央亮起一个高亮点(查询向量,白色发光 bloom)。旁白说"找最近的"时,镜头推近该点,周围一圈同色点被高亮,远处点淡出,最近邻用 Line/Tube 连成星簇。
- 出场方式: 点云 stagger 淡入(非全部同时); 查询点 bloom 浮现
- 音画偏移: 提前0.3s(点云先呈现空间感)
- 素材: 无(纯代码几何体)

### 示例 8：3D 架构爆炸视图（内部结构 -> 爆炸 + orbit）

旁白："Agent Loop 不是黑盒，它由这几个节点串起来，外层还包了检查点。"
- 维度(渲染): 3D(Three.js)
- 实体：Agent Loop 外壳(半透明立方体) / 内部节点(StateGraph、Checkpoint、HITL 三块 3D 积木)
- 动作：揭示内部 = exploded-view(外壳半透明 + 内部块沿轴飞开)
- 镜头: orbit(缓慢环绕一周,展示前后层次)
- 分镜：先一个半透明立方体(外壳)居中。旁白说"由这几节点串起来"时,外壳透明度降到 0.15,内部三块 3D 积木沿不同轴飞开(爆炸视图),每块标功能名。旁白说"外层包了检查点"时,镜头 orbit 绕到背面,露出外壳内侧贴的 Checkpoint 层。最后三块合拢回外壳(反向),收束。
- 出场方式: 外壳 scale-up 落定; 内部块 explode(沿轴 translate 开)
- 音画偏移: 同步
- 素材: 无

### 示例 9：局部→整体揭示（层级/系统 -> 近景引入 → 拉远收束）

旁白："别只盯这一个工具节点，把它拉远，你会发现它只是整张图里的一环。"
- 维度(渲染): 2D
- 实体：单个工具节点(tool_node) / 整张状态图(graph,含多个节点+边)
- 动作：整体关系 = 揭示 -> pull-back(从单点拉远露出全图)
- 镜头: 近景引入(开场镜头贴在 tool_node 上,占满屏看内部"调用/返回") → 拉远收束(父 Group 整体 scale 缩小,tool_node 退成图中一环,周围节点+连线陆续浮现)
- 分镜：开场父 Group scale 放大到 tool_node 占满屏(看到节点内部细节)。旁白说"拉远"时,父 Group 整体 scale 缩小(拉远),tool_node 退到左侧一格,周围一圈同色节点与连线 stagger 淡入,最终铺成完整状态图。tool_node 高亮为"当前所在",其余节点 dim。镜头全程内容驱动(局部→整体),无任何装饰晃动。
- 出场方式: tool_node 居中 scale-up 落定(近景); 拉远后其余节点 stagger 淡入成图
- 音画偏移: 同步(拉远随旁白"拉远"触发)
- 素材: 无
